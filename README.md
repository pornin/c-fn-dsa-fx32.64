# FN-DSA, Experimental Fixed-Point Implementation

FN-DSA is a new *upcoming* post-quantum signature scheme, currently
being defined by NIST as part of their [Post-Quantum Cryptography
Standardization](https://csrc.nist.gov/pqc-standardization) project.
FN-DSA is based on the [Falcon](https://falcon-sign.info/) scheme.

This implementation uses fixed-point operations, as described in [eprint
2026/1531](https://eprint.iacr.org/2026/1531); in the terminology of
that paper, it is a "type 1 fixed-point 32.64" implementation. The
overall structure is the same as
[*c-fn-dsa-alt*](https://github.com/pornin/c-fn-dsa-alt) (described in
[eprint 2026/1915](https://eprint.iacr.org/2026/1915), and thus inherits
the low RAM usage of that code (RAM usage is still somewhat increased,
e.g. from 11 to 15 kB for signing with FN-DSA-512, because fixed-point
32.64 values are 12 bytes each, which is larger than the 8 bytes for an
IEEE-754 'binary64' value). Additionally, this code contains some
support for expanded private keys, i.e. precomputing "Falcon trees",
which consumes more RAM but yields better performance, especially when
generating several signatures with the same private key. Finally,
key-recovery and message-recovery mode, as described in [eprint
2026/420](https://eprint.iacr.org/2026/420), are also implemented (with
the same RAM requirements as standard mode, and only a slight CPU
overhead).

**WARNING:** As these lines are written, the initial draft for the
FN-DSA standard (future FIPS 206) has not been published yet. This code
is interoperable with [*c-fn-dsa*](https://github.com/pornin/c-fn-dsa)
and [*c-fn-dsa-alt*](https://github.com/pornin/c-fn-dsa-alt), in the
sense that key pairs generated by any of these implementations also work
with the other two, and signatures by one implementation can be
successfully verified by the other two. When using explicit seed values
(deterministic usage), they produce different signature values for the
same seed: this is on purpose, to avoid information leaks due to small
differences in computing precision leading to divergences in the
sampling process. *c-fn-dsa* represents my best guess of what the
FIPS 206 draft will look like, but there is no guarantee that I got
it right; moreover, NIST has already announced that it wants to move
to fixed-point computations, thus *c-fn-dsa* will necessarily become
non-compliant at some point. Key-recovery and message-recovery modes
are not part of any standard or announced future standard, so these
cannot be compliant to anything. Everything here is experimental;
use at your own risk.
